   224→   224→## 4. VULNERABILITY FINDINGS
   225→   225→
   226→   226→### F-1: refreshToken Missing from Login/Signup Response Body [MEDIUM]
   227→   227→- **File:** api/v1/auth/login/route.ts:136, api/v1/auth/signup/route.ts:117
   228→   228→- **Detail:** Local code includes `refreshToken` in the JSON response body, but the live deployment (hubspherev3.vercel.app) does NOT return it. The refreshToken IS correctly set in httpOnly cookies (verified via Set-Cookie headers). This causes a functional issue: the client-side `apiFetch` refresh logic (auth-client.ts:71-76) calls `/api/v1/auth/refresh` with `credentials: 'include'` but without a body, relying on the httpOnly cookie — this works in browsers but the response body discrepancy suggests the deployed code is stale (not matching local HEAD commit 16769e5).
   229→   229→- **Impact:** Token refresh from non-browser clients (mobile apps, CLI) would fail since they can't send httpOnly cookies. Browser users are NOT affected.
   230→   230→- **Recommendation:** Verify Vercel deployment is current. Consider re-deploying or triggering a redeploy.
   231→   231→
   232→   232→### F-2: Tokens Stored in localStorage Alongside httpOnly Cookies [LOW]
   233→   233→- **File:** auth-client.ts:5-6, 15-16
   234→   234→- **Detail:** `setTokens()` stores both accessToken and refreshToken in localStorage in addition to the httpOnly cookies. If an XSS vulnerability is ever introduced, the attacker can steal tokens from localStorage. The httpOnly cookies provide the real protection.
   235→   235→- **Impact:** Redundant attack surface. If XSS occurs, localStorage tokens are exfiltratable (though httpOnly cookies are not).
   236→   236→- **Recommendation:** Remove localStorage token storage. Use only httpOnly cookies for both tokens. The `getAccessToken()` function should read from a cookie or from memory only.
   237→   237→
   238→   238→### F-3: env.ts Runtime Fallback to Empty JWT_SECRET [MEDIUM]
   239→   239→- **File:** env.ts:60
   240→   240→- **Detail:** `isBuildTime = process.env.NEXT_PHASE === 'phase-production-build' || !process.env.DATABASE_URL`. If `DATABASE_URL` is empty at production runtime (e.g., env var misconfiguration), then `isBuildTime=true`, and missing `JWT_SECRET` only produces a `console.warn` instead of throwing. The app would start with `JWT_SECRET=''`.
   241→   241→- **Impact:** All JWTs would be signed with an empty secret, allowing anyone to forge tokens.
   242→   242→- **Recommendation:** Separate the build-time check from the DATABASE_URL check. Use only `NEXT_PHASE` for build-time detection.
   243→   243→
   244→   244→### F-4: Health Endpoint Information Disclosure [LOW]
   245→   245→- **File:** api/v1/system/health/route.ts:7
   246→   246→- **Detail:** Exposes server `uptime` (seconds since process start), which reveals server restart patterns.
   247→   247→- **Impact:** Minimal. An attacker could determine when the server was last restarted.
   248→   248→- **Recommendation:** Remove `uptime` from the public health endpoint or move it behind authentication.

   415→   415→### 2.6 Schema Issues Found
   416→   416→
   417→   417→**S-1: No Prisma Enum Definitions — All Status Fields Use Plain String [MEDIUM]**
   418→   418→- **Files:** prisma/schema.prisma (throughout, 35+ fields)
   419→   419→- **Detail:** Status fields like `status String @default("ACTIVE")` use plain strings instead of Prisma enums. Values like ACTIVE/INACTIVE/SUSPENDED, NEW/QUALIFIED/WON/LOST, etc. are defined only in code comments.
   420→   420→- **Impact:** No database-level constraint on valid values. Any arbitrary string can be inserted. Loss of type safety in Prisma client.
   421→   421→- **Recommendation:** Define `enum TenantStatus { ACTIVE SUSPENDED TRIAL }`, `enum LeadStatus { NEW QUALIFIED ... }`, etc. in the schema.
   422→   422→
   423→   423→**S-2: Employee → User Cascade Delete May Delete User Account [HIGH]**
   424→   424→- **File:** prisma/schema.prisma:913
   425→   425→- **Detail:** `user User @relation("EmployeeProfile", fields: [userId], references: [id], onDelete: Cascade)` — Deleting an Employee record will cascade-delete the associated User account, which would also cascade-delete all their Memberships, RefreshTokens, and other user data.
   426→   426→- **Impact:** Accidental employee deletion would lock the user out of the system entirely.
   427→   427→- **Recommendation:** Change to `onDelete: Restrict` to prevent deleting an employee if they have a linked user account, or `onDelete: SetNull` (but this requires making userId nullable).
   428→   428→
   429→   429→**S-3: StageHistory Missing tenantId [LOW]**
   430→   430→- **File:** prisma/schema.prisma:603-617
   431→   431→- **Detail:** StageHistory has no tenantId field. It's only reachable via Deal (which is tenant-scoped), but direct queries would lack tenant filtering.
   432→   432→- **Impact:** Minimal — StageHistory is always queried through a parent Deal. But if code ever queries StageHistory directly without joining through Deal, it could return cross-tenant data.
   433→   433→- **Recommendation:** Add `tenantId String @map("tenant_id") @db.Uuid` and a corresponding `@@index([tenantId])`.

   453→   453→
   454→   454→### 4.1 Deal Metrics in CRM Dashboard
   455→   455→- **File:** api/v1/crm/dashboard/route.ts:62-66
   456→   456→- **Detail:** `db.deal.findMany({ where: { tenantId, archived: false }, select: { stage: true, value: true } })` fetches ALL non-archived deals into memory to compute pipeline value metrics.
   457→   457→- **Impact:** O(n) memory for deal count. Acceptable for small/medium tenants but could be slow with thousands of deals.
   458→   458→- **Recommendation:** Replace with `db.deal.groupBy({ by: ['stage'], _sum: { value: true }, where: ... })` which the route already does at line 100. The separate `findMany` at line 62 appears redundant with the `groupBy` at line 100.

   462→   462→- **Detail:** Each role returns a full `permissions[]` array with 20-100+ permission strings. With 13 roles, the response exceeds 15KB.
   463→   463→- **Impact:** Large response payload on every roles list request.
   464→   464→- **Recommendation:** Paginate roles, or split permissions into a separate endpoint.

   467→   467→- **File:** api/v1/super-admin/audit/route.ts
   468→   468→- **Detail:** Audit logs include `actor` and `tenant` objects. With high audit volume, the join adds latency.
   469→   469→- **Impact:** Moderate — PostgreSQL handles these joins efficiently with proper indexes.
