   415→### 2.6 Schema Issues Found
   416→
   417→**S-1: No Prisma Enum Definitions — All Status Fields Use Plain String [MEDIUM]**
   418→- **Files:** prisma/schema.prisma (throughout, 35+ fields)
   419→- **Detail:** Status fields like `status String @default("ACTIVE")` use plain strings instead of Prisma enums. Values like ACTIVE/INACTIVE/SUSPENDED, NEW/QUALIFIED/WON/LOST, etc. are defined only in code comments.
   420→- **Impact:** No database-level constraint on valid values. Any arbitrary string can be inserted. Loss of type safety in Prisma client.
   421→- **Recommendation:** Define `enum TenantStatus { ACTIVE SUSPENDED TRIAL }`, `enum LeadStatus { NEW QUALIFIED ... }`, etc. in the schema.
   422→
   423→**S-2: Employee → User Cascade Delete May Delete User Account [HIGH]**
   424→- **File:** prisma/schema.prisma:913
   425→- **Detail:** `user User @relation("EmployeeProfile", fields: [userId], references: [id], onDelete: Cascade)` — Deleting an Employee record will cascade-delete the associated User account, which would also cascade-delete all their Memberships, RefreshTokens, and other user data.
   426→- **Impact:** Accidental employee deletion would lock the user out of the system entirely.
   427→- **Recommendation:** Change to `onDelete: Restrict` to prevent deleting an employee if they have a linked user account, or `onDelete: SetNull` (but this requires making userId nullable).
   428→
   429→**S-3: StageHistory Missing tenantId [LOW]**
   430→- **File:** prisma/schema.prisma:603-617
   431→- **Detail:** StageHistory has no tenantId field. It's only reachable via Deal (which is tenant-scoped), but direct queries would lack tenant filtering.
   432→- **Impact:** Minimal — StageHistory is always queried through a parent Deal. But if code ever queries StageHistory directly without joining through Deal, it could return cross-tenant data.
   433→- **Recommendation:** Add `tenantId String @map("tenant_id") @db.Uuid` and a corresponding `@@index([tenantId])`.

   454→### 4.1 Deal Metrics in CRM Dashboard
   455→- **File:** api/v1/crm/dashboard/route.ts:62-66
   456→- **Detail:** `db.deal.findMany({ where: { tenantId, archived: false }, select: { stage: true, value: true } })` fetches ALL non-archived deals into memory to compute pipeline value metrics.
   457→- **Impact:** O(n) memory for deal count. Acceptable for small/medium tenants but could be slow with thousands of deals.
   458→- **Recommendation:** Replace with `db.deal.groupBy({ by: ['stage'], _sum: { value: true }, where: ... })` which the route already does at line 100. The separate `findMany` at line 62 appears redundant with the `groupBy` at line 100.

   462→- **Detail:** Each role returns a full `permissions[]` array with 20-100+ permission strings. With 13 roles, the response exceeds 15KB.
   463→- **Impact:** Large response payload on every roles list request.

   468→- **Detail:** Audit logs include `actor` and `tenant` objects. With high audit volume, the join adds latency.
